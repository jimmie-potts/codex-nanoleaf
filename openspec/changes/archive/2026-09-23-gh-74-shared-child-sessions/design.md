## Context

The shared snapshot gives each session a full identity, an evidenced `parent` and owner-derived `children` counts of fresh active and uncertain children. Codex subagent hooks carry `agent_id`, so the owner records a separate child session with an unknown turn. Its notices can clear only by explicit acknowledgment. The consumer projected every snapshot session as its own task.

## Decision

Group sessions into presented tasks before projection. A task key is a top-level session: one whose parent is unknown, top-level or ambiguous. Each child joins its nearest top-level ancestor present in the snapshot. The walk up the parents is guarded against cycles. The task status is computed from the top-level session's own activity, notices, read evidence and turn, together with the union of attention across the task. Working also counts the owner's `children.active`, which already excludes uncertain and stale children. The consumer does not interpret provider events or recompute the owner's child counts.

A task is current only when a current member supplies its displayed status: the member holding the displayed alert, or the active top-level session or a current active child for working. For unread and idle, only the top-level session counts. Otherwise the existing steady-color rule keeps the last status. Two exceptions let current evidence through. First, when the current members that supplied a retained status no longer supply it, the task takes its new status, still steady and uncertain. Second, a subagent alert that outranks the retained status is shown steadily instead of hidden. The ranking is blocked, question, working, unread, idle. Working follows the owner's `children.active` count, which by design never counts uncertain children as active. So when a subagent goes silent under a current parent, the task follows the parent's current evidence, as the Hub's own Tidbyt consumer does. A hold on the retained working status was tried and removed: every rule for when to release it depended on the order in which the parent's end and the child's silence arrived. When the parent is uncertain too, the ordinary steady-color rule applies. Removal that the owner makes without fresh evidence, through recovery or ambiguity, still takes effect. The #72 owner-recovery exception considers approvals from the whole prior task.

Each child joins the topmost ancestor present in the snapshot, whatever the snapshot order. If that top has a missing parent, or the parents form a cycle, the group is an orphan keyed by its top or by the cycle's smallest key. An orphan is presented only while it has blocked or question attention. This keeps an unattributable subagent alert visible without restoring permanent unread children.

## Failure and recovery

Rows of child sessions that the earlier projection created are no longer live, so the existing deletion removes their session, activity, task, comet and slot rows. Other tasks keep their slots, epochs and task preferences. Modes, scenes, Line preferences and device rows are untouched. The freed Lines follow ordinary allocation. Feed loss, invalid snapshots and resync keep their current behavior. Parentage that the owner marks ambiguous leaves the child top-level, which matches the owner's counts. Rolling back the source restores the earlier presentation on the next snapshot, and no stored data migrates.
